🐻 Codelab: Conecta tu app Flutter + Firebase a una API REST de Spring Boot

    Introducción: ¿qué vas a construir?

    ⏱ 5 min

    En este codelab vas a conectar dos proyectos que ya conoces:

    • Frontend (Flutter): la app login_bear_animation con el osito animado en Rive.
    • Backend (Spring Boot): la API market-backend que expone los productos guardados en PostgreSQL.

    Al terminar, tu app hará este recorrido completo:

    ✍️ Usuario escribe correo y contraseña→ ⏳ CircularProgressIndicator→ 🔐 Firebase Auth valida→ 🐻 Osito celebra→ 🧭 Navigator cambia de pantalla→ 🌐 GET /products a Spring Boot→ 📋 Lista de productos

    Lo que aprenderás

    • Cómo levantar y probar una API REST de Spring Boot.
    • Cómo inicializar Firebase en Flutter de forma segura (sin subir tus llaves a GitHub).
    • Qué es la asincronía en Dart: Future, async y await.
    • Cómo moverte entre pantallas con Navigator.
    • Cómo hacer una petición HTTP y convertir (parsear) el JSON que responde el servidor.
    • Qué es CORS, por qué bloquea tu app y cómo arreglarlo en Spring Boot.

    • Tu app Web </> registrada y los 4 valores: apiKey, appId, messagingSenderId, projectId.

    ⏱ 8 min

    Antes de que Flutter pueda pedir datos, el backend tiene que estar encendido. Piensa en el backend como un restaurante: si la cocina está cerrada, no importa qué tan bonito sea el menú (la app), nadie recibe comida.

    Guarda tus llaves en firebase_options.dart

    ⏱ 5 min

    En clase obtuviste 4 valores de Firebase Console. En lugar de pegarlos directamente en main.dart, los guardaremos en un archivo aparte. ¿Por qué? Porque así lo podemos esconder de GitHub, igual que hicimos con application-dev.properties en el backend.

    1. Crea el archivo

    Dentro de la carpeta lib/, crea un archivo nuevo llamado firebase_options.dart y pega lo siguiente, reemplazando los textos por tus valores reales:

    lib/firebase_options.dart
    import 'package:firebase_core/firebase_core.dart';

// Credenciales del proyecto de Firebase (Este archivo se ignora en .gitignore)
const FirebaseOptions firebaseOptions = FirebaseOptions(
  apiKey: 'PEGAR_API_KEY_AQUI',
  appId: 'PEGAR_APP_ID_AQUI',
  messagingSenderId: 'PEGAR_SENDER_ID_AQUI',
  projectId: 'PEGAR_PROJECT_ID_AQUI',
);
    📌 ¿De dónde saco cada valor? Firebase te mostró un bloque en JavaScript (const firebaseConfig = {...}). No copies todo el bloque, solo el texto que está entre comillas de estas 4 propiedades. Las demás (authDomain, storageBucket, measurementId) no las necesitamos.

    ¿Qué es esto? firebaseOptions es una constante (const) de tipo FirebaseOptions: un "paquete" con tus 4 datos que luego le entregaremos a Firebase en main.dart.

    2. Escóndelo de GitHub

    Abre el .gitignore de tu proyecto Flutter y agrega al final:

    .gitignore
    # Firebase credentials (No subir llaves al repositorio)
lib/firebase_options.dart
**/google-services.json
**/GoogleService-Info.plist
    ⚠️ Si ya lo habías subido... .gitignore solo ignora archivos que Git todavía no rastrea. Si ya hiciste commit de firebase_options.dart, ejecuta git rm --cached lib/firebase_options.dart y vuelve a hacer commit.

    Inicializa Firebase en main.dart

    ⏱ 8 min

    Firebase debe "encenderse" una sola vez, antes de que se dibuje cualquier pantalla. El mejor lugar es la función main(), el punto de arranque de toda app de Flutter.

    Código completo

    lib/main.dart
    import 'package:flutter/material.dart';
import 'package:firebase_core/firebase_core.dart';
import 'firebase_options.dart';
import 'screens/login_screen.dart';

Future<void> main() async {
  // Encender el puente nativo antes de usar Firebase
  WidgetsFlutterBinding.ensureInitialized();

  // Inicializar Firebase usando las credenciales de firebase_options.dart
  await Firebase.initializeApp(options: firebaseOptions);

  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      title: 'Flutter Demo',
      theme: ThemeData(colorScheme: .fromSeed(seedColor: Colors.deepPurple)),
      home: const LoginScreen(),
    );
  }
}

    Línea por línea

    CódigoExplicación
    import 'firebase_options.dart';Trae la constante firebaseOptions que creaste en el paso anterior.
    Future<void> main() asyncAntes era void main(). Ahora es asíncrona porque dentro vamos a esperar a Firebase. (Lo explicamos a fondo más adelante.)
    WidgetsFlutterBinding.ensureInitialized();Enciende el "puente" entre Dart y el sistema operativo (Android/iOS/Web). Normalmente lo hace runApp(), pero como Firebase se ejecuta antes, hay que encenderlo manualmente.
    await Firebase.initializeApp(options: firebaseOptions);Conecta la app con tu proyecto de Firebase usando tus 4 llaves. El await hace que la app espere a que termine antes de seguir.
    runApp(const MyApp());Ya con Firebase listo, dibuja la app (empezando por LoginScreen).
    🚗 Analogía ensureInitialized() es girar la llave para encender el tablero del auto; Firebase.initializeApp() es conectar el GPS; runApp() es arrancar el motor y empezar a manejar. Si intentas conectar el GPS sin tablero encendido, Flutter truena con el error "Binding has not yet been initialized".

    Entendiendo la asincronía: Future, async y await

    ⏱ 10 min

    Antes de tocar el Login, necesitas entender el concepto más importante de este codelab. Hablar con Firebase o con Spring Boot tarda: los datos viajan por la red. Puede tardar 50 milisegundos o 5 segundos.

    El problema

    Si Flutter se quedara "congelado" esperando la respuesta, tu app dejaría de responder: el osito no se movería, los botones no funcionarían y el sistema podría mostrar "La app no responde". Por eso Dart usa programación asíncrona.

    🍔 Analogía: el restaurante de comida rápida

    1. Pides una hamburguesa y te dan un ticket con número. Ese ticket es un Future: una promesa de que "en el futuro" tendrás tu hamburguesa (o te dirán que se acabó).
    2. Mientras esperas, puedes revisar tu celular. La app sigue dibujando la pantalla y animando al osito.
    3. Cuando gritan tu número, recoges tu comida. Eso es await: "aquí me espero hasta que el ticket esté listo y entonces tomo el resultado".

    Las 3 palabras clave

    PalabraSignificadoEjemplo en nuestro proyecto
    Future<T>Un valor de tipo T que llegará después. Future<void> = "terminará después, pero no devuelve nada".Future<List<dynamic>> fetchProducts() → "algún día te daré una lista".
    asyncSe pone en la firma de la función. Le avisa a Dart: "dentro de esta función voy a usar await". Toda función async devuelve un Future.Future<void> _onLogin() async { ... }
    awaitPausa solo esa función (no toda la app) hasta que el Future se complete, y te entrega el valor.final response = await http.get(...);

    Comparación: sin await vs. con await

    ❌ Sin await (incorrecto)
    final response = http.get(Uri.parse('$baseUrl/products'));
// response NO es la respuesta, es el "ticket" (Future<Response>)
print(response.statusCode); // ERROR: Future no tiene statusCode
    ✅ Con await (correcto)
    final response = await http.get(Uri.parse('$baseUrl/products'));
// Ahora sí: response es la respuesta real (Response)
print(response.statusCode); // 200

    ¿Y si algo sale mal? try / catch

    Un Future puede terminar con éxito o con error (contraseña incorrecta, sin internet, servidor apagado...). Para atrapar esos errores usamos try / catch:

    try {
  await algoQueTarda();   // si funciona, sigue aquí abajo
  print('¡Éxito!');
} catch (e) {
  print('Falló: $e');     // si falla, salta directo aquí
}
    📌 Regla de oro Si usas await dentro de una función, esa función debe llevar async. Y si la función es async, su tipo de retorno debe ser Future<...>.

    🧭 ¿Qué es Navigator? (¡Primera vez!)

    En Flutter, cada pantalla es un widget, y las pantallas se acomodan como una pila de platos (en inglés stack). El Navigator es quien administra esa pila:

    Método¿Qué hace con la pila?¿Cuándo usarlo?
    Navigator.pushPone una pantalla nueva encima. La anterior sigue debajo.Ir a "Registro" o "Detalle de producto": el usuario puede regresar con la flecha ←.
    Navigator.popQuita la pantalla de arriba y regresa a la de abajo.Botón "Regresar" o "Cancelar".
    Navigator.pushReplacementReemplaza la pantalla actual por la nueva. La anterior se destruye.Después de un login: no queremos que el usuario regrese al Login con la flecha ←.
    Con push
    ProductsScreen (arriba)
    LoginScreen (sigue abajo)
    ← regresa al Login 😕
    Con pushReplacement ✅
    ProductsScreen (única)
    LoginScreen (destruida)
    ← no hay a dónde regresar 👍

    6.2 La función fetchProducts()

    lib/screens/products_screen.dart
      // 6.2 Función para pedir la lista de productos al endpoint GET /products
  Future<List<dynamic>> fetchProducts() async {
    final response = await http.get(Uri.parse('$baseUrl/products'));

    if (response.statusCode == 200) {
      return jsonDecode(response.body);
    } else {
      throw Exception('Error al cargar productos de la API');
    }
  }

    🔍 Desarmando la función línea por línea

    CódigoExplicación
    Future<List<dynamic>>"Prometo que en el futuro te daré una lista de elementos de cualquier tipo". dynamic significa que Dart no sabe de antemano qué hay adentro (lo sabremos al leer el JSON).
    asyncPorque dentro usamos await.
    Uri.parse('$baseUrl/products')Arma la URL completa: http://localhost:8090/products. El $ inserta el valor de la variable dentro del texto. Uri.parse convierte ese texto en una dirección que http entiende.
    await http.get(...)Hace la petición GET (la misma que hiciste en el navegador / Postman) y espera la respuesta.
    response.statusCodeEl código de estado HTTP. 200 = OK. Otros comunes: 404 = no encontrado, 500 = error del servidor.
    response.bodyEl cuerpo de la respuesta: el JSON, pero como texto plano (String).
    jsonDecode(response.body)Parsea el texto y lo convierte en estructuras de Dart.
    throw Exception(...)Si el servidor no respondió 200, "lanzamos" un error. El FutureBuilder lo atrapará en el siguiente paso.

    products_screen.dart: dibujar la respuesta con FutureBuilder (pasos 6.3 – 6.4)

    ⏱ 12 min

    Tenemos un problema: el método build() tiene que devolver un widget de inmediato, pero los productos llegarán "después". ¿Qué dibujamos mientras tanto? Para eso existe FutureBuilder.

    6.3 y 6.4: el método build

    lib/screens/products_screen.dart
      @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: AppBar(title: const Text('Productos de Spring Boot')),
      // 6.3 FutureBuilder: espera la respuesta de la API y dibuja el resultado
      body: FutureBuilder<List<dynamic>>(
        future: fetchProducts(),
        builder: (context, snapshot) {
          // Mientras responde el servidor, mostrar indicador de carga
          if (snapshot.connectionState == ConnectionState.waiting) {
            return const Center(child: CircularProgressIndicator());
          }

          // Si hubo un error de conexión
          if (snapshot.hasError) {
            return Center(child: Text('Error: ${snapshot.error}'));
          }

          final products = snapshot.data ?? [];

          // 6.4 Mostrar los elementos de la base de datos en una lista sencilla
          return ListView.builder(
            itemCount: products.length,
            itemBuilder: (context, index) {
              final product = products[index];
              return ListTile(
                title: Text(product['name'].toString()),
                subtitle: Text('Stock: ${product['stock']}'),
                trailing: Text('\$${product['price']}'),
              );
            },
          );
        },
      ),
    );
  }
}

    🎬 Cómo funciona FutureBuilder

    Recibe dos cosas:

    • future: el "ticket" que va a vigilar → fetchProducts().
    • builder: una función que se ejecuta cada vez que cambia el estado del ticket y decide qué dibujar.

    El parámetro snapshot es una "foto" del estado actual del Future:

    EstadoCómo lo detectasQué dibujamos
    ⏳ Esperandosnapshot.connectionState == ConnectionState.waitingCircularProgressIndicator
    ❌ Fallósnapshot.hasErrorTexto con snapshot.error
    ✅ Llegaron los datossnapshot.data trae la listaListView.builder

    Detalles finos

    • snapshot.data ?? []: el operador ?? significa "si es null, usa esto otro". Si no llegó nada, usamos una lista vacía para no tronar.
    • ListView.builder: construye solo los elementos visibles en pantalla. Ideal para listas largas.
    • itemCount: products.length: cuántos elementos tiene la lista.
    • products[index]: el producto número index, que es un Map.
    • '\$${product['price']}': \$ imprime un signo de pesos literal; ${...} inserta el valor del precio.

    🔁 Recapitulando la asincronía completa

    1. Se dibuja ProductsScreen y FutureBuilder llama a fetchProducts().
    2. fetchProducts() devuelve un Future (ticket) de inmediato; snapshot está en waiting → se ve el circulito.
    3. En segundo plano, http.get viaja a Spring Boot; Spring consulta PostgreSQL y responde JSON.
    4. await recibe la respuesta, jsonDecode la convierte en List y la función hace return.
    5. El Future se completa → FutureBuilder vuelve a ejecutar builder → ahora con snapshot.data → se dibuja la lista.

    🚩 Punto de control: el error de CORS

    ⏱ 10 min

    Si ejecutaste en Chrome, lo más probable es que el Login haya funcionado perfecto, pero la pantalla de productos muestre:

    Error: ClientException: Failed to fetch, uri=http://localhost:8090/products

    Lo curioso: en Postman y en el navegador sí funcionaba. ¿Qué pasó?

    🔎 Investiga: abre la consola de Chrome

    Presiona F12 (o Cmd + Option + J en Mac) → pestaña Console. Verás algo así:

    Access to fetch at 'http://localhost:8090/products' from origin 'http://localhost:50697' has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present on the requested resource.

    🤔 ¿Qué es CORS?

    CORS (Cross-Origin Resource Sharing, "Intercambio de Recursos entre Orígenes") es una regla de seguridad de los navegadores.

    Un origen es la combinación de protocolo + dominio + puerto. Fíjate:

    Origen
    Tu app Flutter Webhttp://localhost:50697 (el puerto cambia cada vez)
    Tu API Spring Boothttp://localhost:8090

    ¡Son orígenes distintos porque el puerto es distinto! Por seguridad, el navegador no deja que una página lea datos de otro origen, a menos que el servidor dé permiso explícito con una cabecera (header) llamada Access-Control-Allow-Origin.

    🏢 Analogía: el edificio con guardia Tu app (departamento 50697) quiere entrar al departamento 8090 por información. El guardia del edificio (el navegador) pregunta: "¿El del 8090 te autorizó?". Si el 8090 no dejó tu nombre en la lista de visitas (Access-Control-Allow-Origin), el guardia no te deja pasar, aunque el del 8090 sí te hubiera abierto.

    ¿Por qué en Postman sí funcionaba?

    • Postman no es un navegador: no aplica CORS.
    • Al escribir la URL directo en la barra de Chrome, tú estás en el origen 8090; no hay cruce de orígenes.
    • En emulador Android o iOS tampoco verás este error: CORS solo existe en navegadores. Pero tu app Web sí lo necesita, y además es una práctica estándar configurarlo.
    ⚠️ Mismo mensaje, causas distintas En Flutter, Failed to fetch aparece tanto si Spring Boot está apagado como si es un bloqueo de CORS. La consola de Chrome (F12) te dice cuál es: si menciona CORS policy, es CORS; si dice ERR_CONNECTION_REFUSED, el servidor está apagado.

    ✅ Solución: dar permiso desde Spring Boot

    El permiso lo da el backend, no Flutter. Abre ProductController.java y agrega la anotación @CrossOrigin:

    web/controller/ProductController.java
    @RestController
@RequestMapping("/products")
@CrossOrigin(origins = "*")
@Tag(name = "Product", description = "Manage products in the store")
public class ProductController {

    Haz lo mismo en PurchaseController.java si también vas a consumir compras:

    web/controller/PurchaseController.java
    @RestController
@RequestMapping("/purchases")
@CrossOrigin(origins = "*")
public class PurchaseController {

    @CrossOrigin(origins = "*") le dice a Spring: "a cada respuesta de este controlador, agrégale el header Access-Control-Allow-Origin: *". El * significa "cualquier origen puede leerme". El import ya viene incluido en org.springframework.web.bind.annotation.*.

    Alternativa: configuración global (opcional)

    Si tienes muchos controladores, en vez de anotar cada uno puedes crear una clase de configuración:

    web/config/CorsConfig.java (opcional)
    package mx.edu.tecdesoftware.market_backend_2026_3_a.web.config;

import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.CorsRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

@Configuration
public class CorsConfig implements WebMvcConfigurer {
    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOrigins("*")
                .allowedMethods("GET", "POST", "PUT", "DELETE");
    }
}
    🔒 En producción, no uses * "*" está bien para desarrollo y para clase. En una app real debes poner solo los orígenes permitidos, por ejemplo: @CrossOrigin(origins = "https://mi-app.com").
